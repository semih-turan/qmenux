# Operator passkey prerequisite

Status: Local internal implementation; named architecture/security/privacy review and actual enablement pending | 2026-10-26

## Authority and delivery scope

`OperatorPasskeys` supplies concrete application-verified MFA evidence for the existing `OperatorAuthorization` callback. It supplements the required Cloudflare Access identity/edge gate and explicit ACTIVE PLATFORM_ADMIN record. It never maps Access email/groups/amr/iat to MFA, creates an operator, activates one, grants tenant access or permits a high-impact operation. Existing authorization still recognizes only `platform:read`; license/approval/role mutations remain denied.

`OPERATOR_PASSKEY_ENABLED=false` is the default. Disabled, Preview or unsafe-TLS execution returns503 before Access/storage. Access itself retains its independent gate, fixed issuer/audience, fresh signed human identity and key verification. There is no HTTP controller, superadmin BFF, cookie, browser screen or real enrollment/provisioning in this slice. Existing unavailable superadmin shell and API route surface remain unchanged. Actual Access policies, mandatory edge MFA, origin-bypass protection and reviewed privileged transport remain required.

Application WebAuthn gives the API a challenge/signature/user-verification result it can verify directly, rather than interpreting an unverified edge MFA claim. This proposed additional control does not replace planned Cloudflare independent MFA. Architecture/recovery/transport approval is still pending; no provider configuration or real user is enabled by implementing this provider.

## Internal ceremonies

| Use case | Required input and result |
|---|---|
| beginRegistration | Verified Access assertion, random browser binding and independently provisioned enrollment grant; returns fixed-RP creation options |
| finishRegistration | Same identity/browser, challenge and registration response; consumes challenge, verifies registration, atomically stores public credential and spends grant; issues no MFA proof/session |
| beginAuthentication | Verified Access identity/browser and one active credential for that exact application audience; returns fixed-RP authentication options |
| finishAuthentication | Same identity/browser, challenge and assertion response; consumes challenge, verifies signature/flags/counter and atomically updates counter/audit plus new opaque MFA proof |
| policy | Trusted server closure from proof/browser binding; current evidence is checked against the Access identity supplied by OperatorAuthorization, never against browser-selected identity |

All secrets/challenges are43 base64url characters from32 random bytes. Only hashes of grant, challenge, browser binding and proof persist. The future BFF must generate the browser binding, protect it in a host-only Secure/HttpOnly superadmin cookie and enforce exact Origin/CSRF/body/credential isolation; ordinary owner/API/operator session values cannot be substituted for MFA evidence. No existing transport may be connected with a constant-true policy.

Enrollment additionally requires a separately delivered, server-provisioned grant bound to the exact ACTIVE operator/application, with a maximum10-minute validity. There is no grant-creation or recovery endpoint. Public signup/Access alone cannot enroll a key. SQL in tests inserts synthetic grants only in the disposable cluster. A reviewed out-of-band operator provisioning, grant delivery/revocation and recovery process with named accountability is required before real enrollment. Registration is unavailable while an active key already exists; rotation/recovery requires independent authorization, not merely the identity whose key was lost.

RP ID is exactly `superman.qmenux.com`, origin exactly `https://superman.qmenux.com`, algorithms ES256/RS256, attestation none, user verification required and user presence enforced. No configurable parent-domain/alternate-origin acceptance. Non-none attestation is rejected before the general verifier can enter certificate/other-format handling; only Access cert-key fetches occur in the fixture. Creation uses a generic operator label and an opaque operator UUID user handle; no email/Access subject is exposed in options. Authentication is restricted to the identity's stored credential; a returned user handle, when present, must match. Cross-origin/top-origin ceremonies are explicitly denied, including clients that omit crossOrigin. Normal browsers omitting both optional fields remain supported.

Responses are plain closed-field objects bounded16KiB. Client data is decoded with fatal UTF-8; credential IDs must be canonical base64url. Validation failures400 can precede challenge consumption. Once parsed, a matching unexpired challenge is atomically deleted and committed **before** cryptographic verification. A wrong browser/identity/purpose cannot consume someone else's challenge; a signature/UV/origin failure cannot retry the consumed challenge. Proof creation/counter/audit is a separate atomic transaction after successful verification. Unexpected storage errors become minimal503; invalid authority/ceremonies403; Access retains401 for invalid assertions. Provider/SQL details and raw responses are never logged.

## Freshness, concurrency and revocation

Challenges expire in5 minutes and there are at most5 outstanding per operator/application, serialized by the operator row. Beginning a new ceremony removes that operator/application's expired challenges. Enrollment finalization rechecks and spends the grant under the same operator lock as credential/audit insertion; rollback spends nothing. Only one active key and one active proof per operator/application are supported in this development slice. A new successful authentication replaces prior evidence, including in another browser; it does not silently keep several active proofs.

Proofs expire5 minutes after the verified transaction, bind credential/operator/application/browser, and do not extend themselves on use. The existing15-minute operator session is insufficient when its MFA proof expires. Every authorized call still rechecks signed Access, current proof, session and current platform role. Credential counters are rechecked atomically against their pre-verification value, so stale concurrent updates cannot overwrite newer state. Zero-only counters are accepted as the verifier specifies; these do not provide counter-based clone detection.

Any operator update invalidates proofs, outstanding challenges and unused enrollment grants; the existing trigger also revokes sessions. Credential revocation invalidates proofs/challenges/grants/sessions, records REVOKED, and cannot be reversed by restoring its status. Public key/identity/creation fields are immutable and counter rollback is refused. No credential DELETE/TRUNCATE or audit UPDATE/DELETE/TRUNCATE is allowed. Revocation affects subsequent authorization; an already admitted operation is not claimed cancelled in flight.

These five-minute proofs establish ordinary operator MFA, **not** an operation-bound high-impact step-up approval. Audited approval/license/role operations still need a fresh challenge bound to the exact operation and idempotency request. Do not widen the permission allowlist or expose them using this evidence alone.

## Persistence, privacy and rollback

Additive0014 extends only the operator-owned schema, with grant/key/challenge/proof/event tables, default-deny forced RLS and no runtime direct table privileges. Seven fixed-search-path EXECUTE contracts derive the explicit operator/application predicate; three trigger helpers are not runtime-executable. No other module accesses these tables directly. Registered/authenticated events identify the verified operator and credential; a direct-owner revocation event identifies the affected target/key/time, not a falsely asserted human revoker. A future privileged recovery/provisioning audit must record its actual authorized actor/reason.

Security inventory: opaque operator UUID, application audience, public credential ID/key/counter/state, hashed grants/challenges/browser bindings/proofs, expiry and security-event timestamps. Private authenticator keys, biometrics, attestation blobs, extension results, raw Access tokens and MFA proof secrets are not stored here. Attestation none establishes no hardware provenance; synced/software passkeys and zero counters need actual device/security policy review. No legal or physical-device assurance is inferred from synthetic verification.

The existing auth-expiry cron/response/exception scope is unchanged. Challenge storage is capped and cleaned on subsequent own ceremonies; proof storage is bounded to one per provisioned operator/application. Expired records can remain until later use/replacement. General retention/deletion/recovery, expired credential maintenance, abuse controls and monitoring require reviewed delivery before real enablement; no new cron/worker is silently authorized.

Up requires exactly0001–0013 and seeds no operator/grant/key. Down locks all new tables, sets row_security=off to fail rather than miss hidden rows, refuses any data/later schema and never deletes history to force rollback. Remove callers/disable the gate first; retain populated0014 and use a reviewed forward correction.0001–0013 remain unchanged. No cloud migration/manual Neon probe expansion was performed; old probes stay guarded at0009.

## Bound logout (0015, local development)

Both optional proof/browser inputs must be present and valid together; the legacy session-only internal caller is preserved. Future privileged BFF logout must supply all four arguments and clear its cookies only after confirmed success. ## Server-bound privileged browser sessions (0016, local development)

`signInBrowser` creates independent random session/CSRF values after the same Access/current operator/MFA policy checks. Only their hashes persist. `runBrowser` requires the exact CSRF proof belonging to that browser session on every admitted call, alongside Access, fresh browser-bound passkey evidence and current role/session validity. Missing, malformed, wrong and another same-user session's proof deny. The only recognized permission remains platform:read. No approval/license/role mutation is added.

Legacy internal sessions have csrf_hash NULL and retain their original server use. Browser sessions have a non-NULL hash; legacy read/logout contracts explicitly exclude them, and browser lookups cannot accept legacy tokens. `signOutBrowser` verifies the stored CSRF when the own session exists and atomically retires it and matching MFA evidence. Logout remains possible when MFA/session expiry has elapsed; an already absent session is a harmless repeat, and any proof retirement still requires matching verified identity/application/browser. It does not claim CSRF can be checked against a row that has already been deleted. A wrong proof for an existing own session denies without retiring either credential.

0016 adds one nullable constrained hash column and three operator-owned EXECUTE-only functions with fixed paths/no PUBLIC execute. Existing data remain legacy sessions; nothing is retroactively promoted. Existing general session expiry/status/key revocation applies to both kinds. Down locks sessions, sets row_security=off and refuses any browser-bound rows; only after they are retired can it remove the column/functions and restore legacy contracts. It never deletes/restores credentials to force rollback;0001–0015 remain unchanged. Remove browser callers before down.

This is an internal persistence/application prerequisite, not a browser/API adapter or approval to enable privileged routes. Future BFF must select these explicit methods, enforce canonical host/exact Origin/custom header/cookie isolation and double-submit CSRF, protect session/MFA/browser binding in host-only Secure/HttpOnly cookies, and expose no opaque session/MFA value in browser JSON. Actual protected transport, enrollment/recovery, session audit, operation-bound high-impact step-up and named/provider/device/legal review remain. ## Dedicated operator API adapter (unregistered review implementation)

`OperatorAuthController` implements fixed POST operations at `/v1/internal/operator-auth/registration/start`, `/registration/finish`, `/authentication/start`, `/authentication/finish`, `/me` and `/logout`. It is deliberately **not registered in AppModule**: the named-review-before-routes gate above is unchanged. Only the synthetic isolated test module registers it. Current application HTTP probes assert that operator authentication remains404. This code and a successful fixture are not authorization to enable or deploy privileged routes.

When independently registered for reviewed use, the adapter additionally requires explicit OPERATOR_BFF_ENABLED, enabled passkeys, non-Preview/TLS-safe runtime and a distinct43-character OPERATOR_BFF_SECRET. Reusing admin sign-in/onboarding/maintenance credentials fails503. Exactly one matching Bearer authorizes only this fixed server-to-server adapter; signed dedicated Access identity, active platform role, actual passkey and session-bound CSRF remain independently enforced by the real services. There is no browser cookie/API fallback or generic proxy, tenant selection, role/approval/license mutation or grant-generation endpoint.

Every body requires assertion/browser. Registration start adds grant; registration finish adds challenge/response; authentication start needs no other field; authentication finish adds challenge/response and optional previousSession; me/logout add session/csrf/proof. Fields are closed strings, no coercion/control characters. Asserted JWT is bounded8192 characters; secrets/challenge43; serialized credential response16384. Credential response must be the exact compact JSON.stringify result, preventing duplicate/noncanonical serialized fields. It is parsed and still checked by the actual passkey service. The flat outer machine JSON uses existing strict fatal-UTF-8/duplicate key/header/content-type/no-encoding/no-query rules, with a32KiB operator-specific byte bound; admin/onboarding remain8KiB.

Start results return only options. Registration finish returns registered and issues no session. Authentication finish verifies the actual ceremony, then creates the explicit browser session through the verified passkey policy; its server-only result contains session/csrf/proof and900/300-second expiry metadata. These opaque credentials must never pass through the future BFF as browser JSON. Partial failure does not auto-retry a consumed challenge; begin a fresh ceremony. Me returns only verified operator UUID/PLATFORM_ADMIN role; logout uses bound session CSRF and atomic session/proof retirement. Success/errors are no-store/no-referrer, issue no cookie and perform no redirect. Known unsupported methods405/Allow POST; invalid authority401/403, inputs400 and unavailable config503; private diagnostics are sanitized.

The real local fixture runs this adapter over HTTP with the actual signed synthetic Access verifier, native Chromium WebAuthn signatures, real passkey/session services and actual PostgreSQL. It covers authentication start/finish, minimal me, wrong-CSRF denial/preservation, confirmed/idempotent logout and replacement sign-in, key/flag/config/Preview/TLS/purpose/input/duplicate/method rejection. Registration success remains covered at the native service/DB boundary; full registration transport/browser UX is still to verify. Global HTTP probes prove the production module does not register these routes. No real Cloudflare/user/key, canonical-host BFF cookie transport, physical device or deployment evidence is claimed.

Rollback removes fixture/adapter callers before retiring any future machine key across deployments; existing0014–0016/history remain intact. ## Superadmin BFF review implementation (unregistered)

No Next route file registers it; the actual superadmin app still returns404 for operator paths. This preserves the named-review gate and does not enable the preceding API controller. Local handlers/tests are concrete review work, not approval of protected transport or real-user operation.

The handler pins HTTPS superman Host/origin and canonical API URLs, accepts the edge Access assertion header only (no assertion/body/cookie fallback), and forwards it for actual API signature/audience/role verification. It checks syntax/bounds locally without pretending that JWT syntax is verified identity. Both operator flags, a distinct server-only key, non-Preview runtime and verified TLS are required. POST requires exact Origin, JSON, custom header, no encoding, closed bounded flat fields and duplicate-key rejection. Once a browser binding exists, all POST operations require matching readable-CSRF cookie/header. Initial start bootstraps random browser/CSRF values only after successful API options validation; this grants no session or platform permission.

Start accepts empty authentication body or registration grant only. Finish accepts only a compact serialized response: challenge, prior session, browser binding and other authority come from host cookies/server headers. Returned options are validated/reconstructed against fixed RP/origin requirements, UV/algorithms/timeouts, canonical credential/challenge/user encodings, and minimal generic operator labels. Unknown/private fields and known secret reflections are excluded; no generic API response proxy. The API still validates the actual signed ceremony and all stored bindings.

A sent finish attempt retires its challenge cookie even on failure, requiring a new ceremony rather than replay.
