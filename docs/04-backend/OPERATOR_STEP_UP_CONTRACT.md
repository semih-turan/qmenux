# Operation-bound operator step-up

Status: Local internal implementation; architecture/security/privacy review and real enablement pending |2026-10-26

## Server application contract

OperatorPasskeys adds beginStepUp, finishStepUp and runStepUp. They require signed Access identity, an ACTIVE PLATFORM_ADMIN, an unexpired browser session with its stored CSRF and current browser-bound ordinary passkey proof. Existing flag/Preview/TLS guards apply. Ordinary run/runBrowser still recognize platform:read only; no approval/license/role permission is silently added. There is no new HTTP/BFF route, UI, tenant approval, license change, operator provisioning or enabled configuration.

A trusted business adapter supplies OperatorOperation with a closed action, targetId UUID, requestId UUID and payloadHash. Supported action labels are tenant:approve, tenant:reject, license:grant, license:extend, license:suspend, license:revoke and operator:manage. Labels reserve an explicit ceremony purpose, not an operational endpoint or domain authorization. The business adapter must select the action, validate/normalize the complete command (including reason, dates, expected revision and subaction when relevant), derive its canonical payloadHash itself and recompute the same descriptor on every phase. Never accept a browser-selected digest as proof of which command was approved. Binding hashes a deterministic JSON array of action/target/request/payload hash; additional or malformed fields deny400. Target/request UUIDs use lowercase canonical spelling.

beginStepUp returns required-UV fixed-superman WebAuthn authentication options for the current key. A fresh challenge is bound to exact identity/application/session/CSRF/MFA/browser and operation digest. Only one pending challenge and one proof per session are retained; a new start replaces that session's pending challenge and proof, so cancellation requires a fresh ceremony. Expired own records are pruned at start and at most five pending step-up challenges per operator are permitted. This is separate from ordinary registration/authentication challenge storage.

finishStepUp commits matching one-use challenge consumption before invoking the same actual native-credential verification code as ordinary authentication. Bad signatures cannot replay; ordinary challenges cannot finish step-up and step-up challenges cannot finish sign-in. Actual UV/signature/counter/origin/RP checks apply. Successful verification rechecks current authority and counter atomically, updates the credential counter and issues an independent random hashed two-minute proof with a VERIFIED audit event. It does not replace or refresh ordinary MFA. The current five-minute ordinary evidence must still be valid; step-up cannot extend it. Challenge validity is two minutes, browser prompt timeout60 seconds.

runStepUp rechecks exact session/CSRF/browser/current MFA and operation plus the independent proof. It locks the affected operator against concurrent role changes, consumes one matching unexpired proof, records CONSUMED and invokes the trusted transaction callback with a frozen verified operator. Proof consumption, audit and callback database writes commit or roll back together. Concurrent attempts admit exactly one committed effect. Failed transactional work can retry the unexpired proof; consumed success cannot replay. Business contracts must also enforce their own expected revisions, tenant boundaries and durable request-result idempotency. A step-up proof alone does not implement those domain rules.

The callback may call approved transactional application contracts or write an outbox. Do not perform HTTP calls, publish messages, send email or other external side effects inside it: database rollback cannot undo those. No cross-module table access or generic externally callable mutation callback is approved by this internal provider. The current regression writes only an explicitly synthetic fixture table and leaves actual tenants/memberships unchanged.

## Storage, audit and rollback

0019 adds operator-owned forced-default-deny-RLS step_up_challenges, step_up_proofs and append-only step_up_events. Four EXECUTE-only contracts support begin/consume/verify/use; the actor helper is not runtime-executable. Fixed search paths, explicit identity/application predicates and no runtime direct table grants follow existing operator contracts. Stored secrets are hashes; session and ordinary MFA foreign keys cascade invalidation on logout, rotation/replacement, operator/key revocation and session cleanup. Expiry is checked independently at every admitted phase. No expiry revival occurs on status restoration.

Events retain actual verified operator, random session audit UUID, action/target/request/digest, phase and timestamp; no challenge/proof/session token hashes, raw command/reason, browser binding, Access JWT or biometric data. VERIFIED means a credential ceremony succeeded, not that the business action committed. CONSUMED commits only with the transaction callback, but does not itself replace the domain result/reason audit. Data retention/export, event access, alerts and actor/reason-specific provisioning/recovery still need reviewed implementation. No public audit reader or new scheduled cleanup is added.
