# Operator pending-application review and rejection

Status: Local internal implementation; named architecture/security/privacy/legal review and production routing pending |2026-10-26

## Authority and behavior

OperatorApplicationReview is an internal provider with list, beginReject, finishReject and reject. List requires actual signed Access, ACTIVE PLATFORM_ADMIN, current browser session/stored CSRF and browser-bound MFA. UUID cursor pagination defaults20/max100 and returns pending-only minimal application projections; unsubmitted drafts, applicant identity and private review metadata are excluded. No controller/BFF/UI registers privileged review operations yet. Existing operator flags/Preview/TLS and named route gates remain.

Rejection requires target application UUID plus closed {revision,reason,requestId}. Reason is trimmed, single-line, nonempty/max1000 UTF-16 units; revision1..2147483646 and canonical UUID request. The server selects tenant:reject, derives payloadHash from UTF-8 revision:reason, and binds target/request/payload with the existing separate step-up ceremony. The SQL contract derives the identical operation digest itself. Quotes, colons, accented/supplementary characters are covered with a real native signature; browser-selected hashes/actors/statuses cannot substitute.

reject first looks up an already recorded decision for the current verified operator/request. Exact same target/original revision/normalized reason returns the immutable decision without requiring another proof; changed payload or target409. The authenticated replay checks current session/MFA again and grants no new authority. A new decision consumes the bound step-up and locks the application in the same database transaction. Only PENDING_APPROVAL at the expected revision may become REJECTED; draft/already decided/stale409 and missing404. Revision increments once, reviewedAt is server-owned, and verified operator UUID/request/reason are recorded atomically with old/new OPERATOR audit. Concurrent identical retries converge on one recorded result; a lost proof race may perform a bounded read-only replay lookup, never an automatic write retry.

The decision creates no tenant, membership, approval or license, and does not suspend the applicant identity. REJECTED is terminal for this application; applicant edit cannot reopen it. Existing applicant list/create-idempotency/submit replay return the authoritative REJECTED state. The existing admin BFF/parser/screen accept that state and show only generic rejection/no-access wording, including stale submit/create retries. Internal reason/operator/request metadata is not returned to applicants. Another explicit new draft remains governed by existing create behavior; duplicate-business/appeal/reapplication/abuse policy still needs review and no automated reopening is added.

## Transactional module contracts (0020)

Operator owns review_session (current verified browser/MFA lookup) and rejection_actor (matching consumed rejection in the current transaction). Onboarding calls these explicit function contracts and never reads operator tables. Operator helpers read only operator-owned session/proof/audit/role data. Existing ordinary step-up functions continue to own verification/consumption; business SQL cannot select an operator UUID to bypass it.

0020 adds nullable transaction_id to step-up audit, then sets pg_current_xact_id() as the default for future events. Historical events retain NULL and gain no retroactive authority. An indexed CONSUMED rejection with matching operation hash/current transaction and ACTIVE role supplies the verified actor; a later transaction cannot reuse historical consumption. This capability uses no new session setting or unverified GUC actor claim. The actual existing operator lock covers step-up consumption and the business callback. The new contract is proposed ADR022 and remains review-gated before real use; no cross-module direct table join is introduced.

Onboarding adds private rejection metadata, strict three-state consistency and unique (reviewed_by,review_request_id) retry binding. application_events gains actor_kind, with historical events truthfully APPLICANT and new reviews OPERATOR. The trigger retains identity/submitted-name protection and requires the actual transaction capability for pending→rejected. Applicant actor context cannot write decision metadata. Three EXECUTE-only onboarding contracts list/replay/reject; a pure digest helper is not runtime-executable. Existing forced-default-deny RLS/direct table denial and append-only event protections remain.

runStepUp now preserves sanitized NotFoundException/ConflictException from domain callbacks as well as ForbiddenException; unexpected failures remain503. Application transition, domain audit, proof consumption and CONSUMED audit roll back together on failure. A failed write cannot be reported as confirmed; an exact authenticated retry can inspect committed state. Normal MFA/role/session expiry continues to deny replay/read.

Up requires exactly0001–0019 and changes no existing application state or historical decision. Down locks affected application/audit tables with row_security=off and refuses any rejected/operator-reviewed application history or new step-up transaction metadata. Never delete history to force down; retain populated0020 and use reviewed forward correction.0001–0019 and manual Neon guards at0009 remain unchanged. Only disposable local PostgreSQL receives this migration here.
